## Что меняется для нашей работы

1. Выбран один кейс: EKT-консультант. Приоритет - обязательный путь от запроса до проверенного результата за отведённые пять часов. Использование AI-агента прямо указано в дополнительной инструкции участников; это уточнение к прежнему пересказу мастер-промпта.
2. Итоговый код должен быть в репозитории команды, выданном платформой. Наш проверенный remote: `BAITC-Hacks/hack-08ee446c-apexsoft`; private=true, доступ на push подтверждён. Разработка A/B в отдельных ветках, интеграция после проверки.
3. Push не завершает подачу. После него человек переходит на страницу треков, выбирает кейс, нажимает **«Сдать решение»**, заполняет название и описание. Обновление решения возможно до дедлайна. Какая ветка оценивается, этот PDF отдельно не определяет; main - фактическая default branch, а не доказательство правил оценивания.
4. README на русском: название; проблема и аудитория; реализованные функции; основной сценарий; технологии/AI-модель/API; архитектура; пошаговый запуск; повторяемый пример для жюри; данные/интеграции; ограничения; ссылка на развёрнутую версию, только если она существует. Только подтверждённые сведения. Наличие deployed-ссылки условно, а не отдельное требование обязательно развернуть проект.
5. Секреты запрещены в исходниках, репозиториях, презентациях и чатах. Ключи из личного сообщения не передаются B; приложение получает их только в памяти серверного процесса. Перед push проверяем diff и индекс Git на секреты. Репозиторий сохраняем закрытым.
6. Каталог и сервисы используем в рамках доступа, выданного для кейса. Не включаем реальные клиентские/персональные данные в тесты. Для offline-тестов - синтетические карточки; данные каталога в live-режиме считываются через разрешённый API. Пользовательские вложения не пишем на диск; перед передачей текста/фото в OpenAI показываем уведомление и не запрашиваем платёжные данные.
7. AI-результаты проверяем самостоятельно. Только обычные функциональные проверки собственного приложения и ограниченные запросы разрешённого API; никаких сетевых сканирований, нагрузочных тестов инфраструктуры, обходов лимитов или чужих ресурсов.

## Правила участия: действия людей на площадке

По [Правилам зачёта участия](https://drive.google.com/file/d/1GkZG7O9ME2N7BlTZUQ3Ih1l2kstCxbdN/view), с. 1-2: личный бейдж и сканирование входов/выходов; до старта нужно вернуться; после старта нельзя пересаживаться даже внутри своего сектора или переходить в другой. Выходы суммарно до 60 минут с уведомлением стюарда. **Весь последний час нужно быть на площадке**; экстренный выход до пяти минут только с разрешения стюарда. Каждый человек вносит личный вклад. Нельзя уйти до официального завершения. Агенты не подтверждают эти условия за людей.

## Переводы и область достоверности

RU/KZ/EN рассмотрены отдельно. В KZ/EN инструкции участников есть ссылка на видео подачи, в RU она отсутствует; состав требований совпадает. Русский PDF безопасности дополнительно содержит английский текст. В безопасности RU/EN требуют уникальный пароль, KZ - сложный; разумно соблюдать оба свойства. KZ шире формулирует запрет самостоятельной проверки найденной уязвимости (RU/EN - эксплуатации). В ASU KZ иначе разбита нумерация без изменения действий. Это не 18 разных регламентов, а шесть тем с переводами. При конфликте с объявлением организатора люди уточняют правило у организатора. Сам факт чтения не подтверждает check-in, активацию кредитов, состояние сети, прохождение курса или отправку решения.
